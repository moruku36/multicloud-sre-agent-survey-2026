# 障害注入と復旧確認をSREエージェント調査へ加える将来案

**状態：文書上の提案・未実装・未実験。** 新たなクラウド接続、障害注入、権限変更、復旧操作は行っていない。

## 根拠と境界

[Adaptive Ephemeral Chaos Infrastructure for Resilience Validation in AWS Multi-Account Environments](https://ijetcsit.org/index.php/ijetcsit/article/view/654) の出版社PDF全8ページの確認記録によると、AWS複数アカウントの七段階の実験ライフサイクル、復旧検証、競合検出、協調を設計する。15分の事前baseline、標準偏差2倍以内で連続3分の安定、15分未収束時のUNRESOLVED・SNS通知・次実験の停止を条件とする。これらは設計パラメータであり、普遍的な安全保証ではない。第8節は将来の評価方法で、実測結果や実環境の効果は示していない。コードと再現性は未検証。研究リポジトリのサーベイを参照する。AWS複数アカウントと当リポジトリの複数クラウド、また障害実験の制御とLLM自律診断は別の課題である。

既存の[構成・検証計画](architecture-and-validation-plan.ja.md)は診断と実行の境界を分けている。この案はその境界を維持し、**障害注入の終了**と**サービスの復旧確認**を別状態として記録する。

## 将来の設計と検証案

1. クラウド共通の実験状態モデルと、各クラウド固有の障害注入アダプターを分ける。AWS以外への移植は別途設計・評価する。
2. エージェントは計画案と結果要約から始める。実行は隔離された対象、明示承認、許可済み範囲が揃う場合だけ検討する。停止条件とロールバック責任者を事前に定める。
3. 単一APIの成功だけで復旧としない。利用者向けSLI、依存サービス、設定差分、残存資源を継続観測し、欠測を正常扱いしない。
4. 最初は模擬イベント列で競合実験、部分障害、観測欠落、タイムアウトを試す。次段階の比較軸は誤った復旧判定率、復旧時間、残存資源、競合回避、費用とする。
5. 実装判断の前に本文の設計を精査し、再現用構成と実測ログを確認する。原著の将来構想や本案を実装済み機能として記載しない。

無料の初期検討は状態遷移・中断・復旧判定の机上テストに限る。クラウド上での障害実験はこの文書の作成範囲外である。
